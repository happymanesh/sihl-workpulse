TM-FR-058 §1

The CEO Command Centre feed

System shall expose a structured API/event feed of enterprise status for the future CEO Command Centre. The feed excludes Confidential task content by default. BRS Appendix A

An event stream, not a dashboard query. The Command Centre is a separate consumer on its own cadence: it must be able to ask what changed since I last looked without re-deriving the enterprise from scratch, and without workPulse knowing anything about how it renders.

The integration surface is REST rather than tRPC on purpose. tRPC's value is end-to-end types for our web client; this endpoint exists for a consumer built by someone else, on a stack we do not control, possibly years from now.

SurfaceConsumer
GET /command-centre/events?since=<cursor> External Command Centre, via INTEGRATION_SERVICE
GET /command-centre/pulse Same — headline figures with direction of travel
commandCentre.* (tRPC) workPulse's own /command-centre screen

The six conditions that reach a CEO

The governing principle is that this feed must stay quiet. A feed that fires on every overdue task is read once and then ignored — which is worse than not having one, because it converts a real escalation into noise the reader has been trained to skip.

SLA_BREACH Critical & Urgent only A breached Low-priority task is a real fact and a line-manager matter. It belongs in MIS, not in front of the CEO.
ESCALATION_TOP_LEVEL Chain exhausted Intermediate levels are the chain working. The top level is the chain having failed to resolve it — the only part that is genuinely executive.
CRITICAL_OVERDUE 24h past due Below this, the escalation chain has not finished trying.
BLOCKED_BEYOND_THRESHOLD 72h blocked Names the blocking owner, not the assignee. Blocked work is the one case where the person holding the task usually cannot act, and naming them would point the CEO at the wrong desk.
RECURRING_COMPLIANCE_MISSED Always urgent For a BFSI entity approaching listing, a missed filing is not a productivity metric.
PROJECT_HEALTH_DEGRADED On the transition A project amber for a month is a known problem being managed. One that turned amber this morning is news.

Every threshold is an exported constant, so SIHL can calibrate them against real volume rather than argue about them in the abstract.

Two properties enforced in code

  1. Confidentiality is applied at generation, not at read. Every detection query carries isConfidential: false. A consumer holding an integration token has no parameter that widens it, because the excluded rows were never written.

  2. The cursor cannot skip. sequence is a 64-bit value serialised as a string. As a JSON number it would silently lose precision past 253, and a cursor that quietly skips events is the one failure mode a feed must not have.

Events resolve as well as raise. A feed that could only ever accumulate would be unreadable by week three.

TM-FR-059 TM-FR-060 §2

HR appraisal evidence

Given an appraisal cycle opens, when HR views WMP evidence, then no single numeric 'score' field exists. BRS Appendix A — TM-FR-060 acceptance criterion

That criterion is taken literally, in three places:

  • AppraisalEvidence has five component columns and no sixth combining them.
  • The read path returns an explicit compositeScore: null plus a written explanation, so absence cannot be mistaken for an oversight.
  • A test asserts that no numeric key named score, composite or overall appears anywhere in the payload.

Why a snapshot, not a live query

An appraisal conversation must reference a fixed artifact. A figure that moves between HR reading it and the employee being shown it is not evidence — it is an argument. Generation is idempotent per employee and cycle, so there is exactly one artifact and no ambiguity about which one the conversation used.

The asymmetry the BRS asks for

Data flows upward freely for visibility, but only flows into the formal appraisal process through a governed, human-reviewed step. BRS §4.6 — Task → KPI → MIS → Command Centre → Appraisal
ControlHow it is implemented
Generation is restricted HR, Audit or an executive. A line manager is deliberately refused — they read the same figures through the report card, which is symmetric with what the subject sees.
Generation is audited Naming who pulled whose record, and when.
Disclosure is recorded disclosedToSubjectAt is set the moment the subject reads their own. TM-FR-059 stops being a promise and becomes a fact somebody can check — the HR screen shows how many subjects have not yet seen theirs.
Exclusions are disclosed Work removed by an open flag is reported on the snapshot rather than silently shrinking the denominator.
Appendix F §3

SLA-breach prediction

SLA-breach prediction — clearest operational payoff, lowest governance risk. BRS Appendix F — recommended first AI capability

What was built is an explainable additive model, not a fitted one. The naming says so throughout: risk, never confidence or probability.

  1. There is no training data yet. A model fitted on an empty history would be a confident-looking random number.

  2. A supervisor cannot act on “0.82”. They can act on “not started, 70% of the window gone, and this task type breaches a third of the time”. Every factor carries its own contribution, and the screen shows the top four.

  3. It is measurable. Every prediction is recorded against what actually happened when the task settled.

Honesty about accuracy

Accuracy is reported as skill against the base rate, not raw accuracy. If 5% of tasks breach, then “nothing will ever breach” is 95% accurate and completely useless. The screen shows the model's own track record above its predictions, and when skill falls to zero or below it says so in plain words:

On this record the model is not adding information beyond how often work breaches anyway. Weigh it accordingly, and raise it — a model that earns nothing should be recalibrated or retired, not quietly tolerated. Shown on /at-risk when skill ≤ 0

What is not assessed

Settled work, paused work — a paused clock cannot breach while it is paused — and anything with no SLA attached. Predicting breach for something already closed is noise a supervisor has to learn to ignore, which is how a useful signal becomes a dismissed one.

Addendum 02 F3-01..06 §4

The shadow quarter

Status

The weighted composite score now exists in code. It is not in force, and it reaches no surface a manager, HR or an employee can read.

This is not a reversal of the Phase 6 rule that the analytics core has no composite function. That rule still holds and is still tested. The shadow quarter's entire purpose is to answer “would this score have said anything true?” before anyone's appraisal depends on it — and that question cannot be answered without computing the number.

Four structural constraints, none of them a comment

  1. Every export is prefixed shadow, so a call site cannot be mistaken for production scoring when reading a diff.

  2. The only persistence target is ShadowScore, never joined into appraisal evidence. TM-FR-060 stays true while a shadow quarter runs, and a test asserts it.

  3. Reads are Audit only — see the matrix below.

  4. isInForce has no true branch anywhere in the codebase. Publishing the score is a schema and router change with a review, not a flag flip.

Who may read a shadow score

AUDIT Permitted A control the compliance function cannot inspect is not a control.
The subject Refused A number nobody is permitted to act on should not circulate in appraisal season. Telling someone their shadow score and then insisting it does not count is not a control, it is a formality nobody will respect.
Their manager Refused Same, and worse — they are the person who would act on it.
HR Refused Until F3-01..06 is signed off, the weights are this office's draft, not HR's policy. Showing HR a distribution computed under weights they have not agreed invites the sign-off to be retrofitted to the result.
SYSTEM_ADMIN Refused Running the system is not standing to read people's performance — the same reason it cannot read confidential tasks.

What the shadow quarter is actually looking for

Not “is the score low”. The failure this is designed to catch is that the score does not discriminate — if 90% of people land within a couple of points of each other, the model has measured nothing and must not be published, however defensible its arithmetic looks.

The review states a conclusion rather than producing a chart, so it ends in something somebody has to disagree with in writing:

  • Fewer than 20 employees above the volume floor → too few to conclude anything.
  • 10th-to-90th percentile spread below 10 points → barely separates anyone.
  • More than 70% within 5 points of the median → not discriminating.

Advisory only. HR signs off, not the function.

The screen is not in the sidebar

And it renders nothing — not even its headings — until the caller is known to be permitted. Advertising a route every other role would be refused would tell the business that a weighted performance score exists and is being computed on them, which is precisely the impression a shadow quarter is run to avoid creating.

Carried out of Phase 7

Resolved · access

Synapse's role catalogue holds exactly five roles. The four that should map already do. The other six workPulse roles have no Synapse counterpart at all, so they could never have been fixed by adding mapping rows — there was nothing to map from. Pointing one at an existing operational role would have handed confidential-task visibility to whoever runs the support desk.

DEPARTMENT_HEADPROJECT_MANAGEREXECUTIVE EXECUTIVE_RESTRICTEDAUDITINTEGRATION_SERVICE

What was built: a write path for direct grants — the mechanism the schema always anticipated for “grants Synapse has no concept of, notably AUDIT” — mapping administration that refuses a Synapse role code which does not exist, and an access screen that names every role nobody can currently reach.

Guardrails on granting

Self-grant Refused AUDIT and EXECUTIVE_RESTRICTED cannot be granted to yourself. An administrator who could hand themselves AUDIT would make the whole separation theatre — AUDIT exists to watch the people who administer the system. Granting them to someone else stays possible, audited, and visible to Compliance.
Sensitive roles Reason required AUDIT, EXECUTIVE_RESTRICTED, EXECUTIVE and INTEGRATION_SERVICE each need a written reason on the record.
INTEGRATION_SERVICE Not on a person It is for service accounts consuming the Command Centre feed. On someone with an employee record it would be a standing credential nobody reviews.
CLIENT_SELF Never mappable Held by external clients. Mapping it — even to the lowest role — would give customers workPulse accounts and desk cards. Leaving it merely absent invited a future administrator to “complete” the map, so it is refused in code.

What SIHL decides, per role

Six roles are unreachable today, and the access screen leads with that count. There are two ways to close each one, and both are business decisions rather than engineering ones:

  • Create the role in Synapse and map it here. Durable, and right for DEPARTMENT_HEAD, PROJECT_MANAGER and EXECUTIVE, which track the org chart.
  • Grant it directly. Right for AUDIT — BRS Section 18 puts it outside the line hierarchy and Appendix F wants joint CTO and Compliance sign-off — and for EXECUTIVE_RESTRICTED and INTEGRATION_SERVICE.
Conflict · TM-FR-061 vs Addendum 02

TM-FR-061 asks for analytics weighted by Priority and Complexity. Addendum 02 §2 defines a Weighted Task Unit as priorityWeight × (estimatedMinutes ÷ 30) — effort, not complexity. These are not the same thing: a two-hour reconciliation and a two-hour regulatory interpretation take the same time and are not the same work.

What was done: a complexity attribute was added and is captured at task creation. It is not a term in the scoring formula. Changing a signed-off formula unilaterally would be wrong, and capturing the attribute now means the history exists when the amendment lands.
